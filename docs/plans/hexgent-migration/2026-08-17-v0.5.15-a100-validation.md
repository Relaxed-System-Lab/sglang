# 2026-08-17 SGLang v0.5.15 A100 实机验证

## 1. 验证目标

本轮在 6 张 `NVIDIA A100-SXM4-80GB` 的单机 RunPod 上验证 HexAgenT 的
SGLang v0.5.15 移植。代码分支为 `hexgent-v0.5.15`，上游基线为 SGLang
v0.5.15 commit `f63458b5be`。实机 runtime 使用 Pod commit
`7bc2eb468fb49e422c501a7c78282053e2e3deed`；它与本地 commit
`fec60b7b425c589da32f57cb97f60c3cad7bb21e` 的 Git tree 均为
`defa4f3b4f445ac7b1ce3458615260e270c68586`。模型为
Llama-3.1-8B-Instruct BF16，每个
prefill/decode worker 均为 TP1。

验证覆盖：

- Python planner sidecar、Rust PD router、global admission queue 和 worker snapshot；
- Mooncake intra-node NVLink P-D disaggregation；
- ShareGPT、BFCL-v3、HotpotQA/LATS 的固定 token-length DAG replay；
- 同模型、同 GPU、同 SGLang release 的独占 profile SLO；
- baseline 与 HexAgenT 的 workflow SLO ratio、latency、GPU telemetry 和 planner telemetry。

## 2. 跨 worker 调度边界

v0.5.15 并未提供一个可以安全取消 bootstrap、转移 KV 所有权并重建 decode
状态的通用 live-migration primitive。因此当前边界仍然是：

- 请求尚在 router global admission queue、尚未 dispatch 时，可以修改 prefill/decode
  placement；
- dispatch 时创建 bootstrap room 并提交 P/D worker pair；
- 已 dispatch 但仍在 worker waiting queue 的请求可以通过 revision-guarded
  `priority_update` 调整同一 local queue 内的顺序；
- 已 dispatch 的请求不能跨 worker 迁移；prefill、KV transfer 或 decode 开始后同样不能迁移。

相比 v0.5.9，v0.5.15 的 observability 和 PD 代码组织更完整，但并没有改变上述所有权边界。
HexAgenT 仍依靠“尽量晚 dispatch、在 global queue 中重规划”获得跨 worker placement
自由度，而不是在 worker 间搬运已提交请求。

## 3. 环境与配置

| 项目 | 配置 |
| --- | --- |
| OS | Ubuntu 22.04 |
| GPU | 6x A100-SXM4-80GB，NV12 topology |
| 模型 | Llama-3.1-8B-Instruct BF16 |
| Worker TP | TP1 |
| KV backend | Mooncake intra-node NVLink |
| Radix cache | disabled |
| Prefill `max_running_requests` | 32 |
| Decode `max_running_requests` | 128 |
| Decode transfer concurrency cap | 1 per decode worker |
| Planner transfer model | 7 GB/s + 10 ms startup |

每个 worker 日志均明确出现 `Using Intra-Node NVLink transport`。正式 replay 前，
baseline 和 HexAgenT 分别进行独立 warmup，并用唯一 run namespace 隔离 planner DAG state。

## 4. 代码与兼容性修复

本轮验证前后的 v0.5.15 兼容工作包括：

- 保留 v0.5.15 router/runtime CLI 和 Python binding 行为，而不是覆盖为 v0.5.9 实现；
- 移除 v0.5.15 不再接受的旧 disaggregation CLI 参数；
- 使用 container-local Python 安装运行 GPU worker，避免从 network volume 导入源码造成初始化阻塞；
- 构建并使用 A100 Mooncake NVLink telemetry overlay；
- 将 `trace_summary.json` 视为可选派生产物，避免已完成实验在最终复制阶段失败；
- 增加 `CREATE_ARCHIVE=0`，允许实时结果先写 Pod 本地盘，再一次性归档到 network volume；
- 扩展 `calibrate_pd_telemetry.py`，同时解析 v0.5.9 `Req Time Stats` 和 v0.5.15
  `ReqTimeStats` 日志格式。

v0.5.15 的 `transfer_speed` 不是纯 CUDA DMA 指标。Mooncake 未设置
`KVTransferMetric.transfer_latency_s` 时，SGLang 用
`completion_time - prefill_transfer_queue_entry_time` 计算该字段，源码注明它只覆盖
last-chunk boundary。因此校准结果将其命名为 `prefill_transfer_observation`，不称为
native copy。纯 NVLink copy 仍应使用 Mooncake 内部 CUDA-event telemetry 或独立 P2P
微基准。日志字段虽然显示 `MB` 和 `GB/s`，源码实际按 MiB 和 GiB/s 计算；校准器已按
二进制单位换算为 bytes 和 bytes/s。

拓扑和 arrival rate 沿用 A100 v0.5.9 的已验证压力点：

| --- | --- | ---: |
| ShareGPT | 1P+5D | 24 workflow/s |
| BFCL-v3 | 4P+2D | 0.3 workflow/s |
| HotpotQA/LATS | 1P+5D | 0.19 workflow/s |

### 7.1 Workflow SLO ratio

| Trace | Metric | Baseline | HexAgenT | Relative change |
| --- | --- | ---: | ---: | ---: |
| ShareGPT | Mean | 1.3572x | 1.3725x | +1.13% |
| ShareGPT | P95 | 1.6225x | 1.5845x | **-2.34%** |
| ShareGPT | P99 | 2.2721x | 2.3857x | +5.00% |
| BFCL-v3 | Mean | 1.4335x | 1.3440x | **-6.24%** |
| BFCL-v3 | P95 | 2.4072x | 1.9943x | **-17.15%** |
| BFCL-v3 | P99 | 2.8209x | 2.1582x | **-23.49%** |
| HotpotQA | Mean | 1.8238x | 1.8260x | +0.12% |
| HotpotQA | P95 | 2.1819x | 2.1988x | +0.77% |
| HotpotQA | P99 | 2.3044x | 2.2354x | **-2.99%** |

ShareGPT 和 BFCL 复现了 P95 改善；HotpotQA 的 pooled P95 略差，但 P99/max 改善。
Hotpot 使用两轮相反 mode 顺序，共 40 个 workflow-runs；仍然不应将 0.77% 的 P95
差异解释为显著回归或将 2.99% 的 P99 改善解释为全面胜出。需要更多不同 Hotpot
workflows 和独立重复计算置信区间。

## 8. GPU 利用率与 placement

所有参与计算的 GPU 均曾短时达到 100% utilization，说明 worker 确实进入了高负载
kernel 阶段，但这个峰值本身不足以证明 `max_running_requests` 从未限制 continuous
batching；严格判断仍需同时使用 running-request、batch-token、queue-depth 和吞吐
telemetry。本轮配置采用 prefill 32、decode 128，以下全程均值主要反映 trace
barrier/burst 和 placement 分布：

- ShareGPT baseline/HexAgenT：prefill 56.9%/55.8%；五张 decode 平均约
  75.0%/76.6%。
- BFCL baseline：四张 prefill 为 55.5%、0%、32.8%、27.6%；两张 decode 为
  42.3%、30.2%。HexAgenT telemetry run 为 34.0%、53.9%、28.8%、1.3% 和
  34.8%、46.5%。4P placement 仍存在一张近空闲 prefill worker，后续应继续校准
  availability/tie-breaking；本轮 tail 改善并不是由完美负载均衡产生。
- Hotpot baseline 实际只持续使用 2/5 张 decode worker；HexAgenT 将请求分布到全部
  5 张 decode worker，但仍集中在其中两张。HexAgenT 扩大了 placement 覆盖范围，
  尚未实现均匀负载。

Hotpot 的 width-5 fan-out 与 barrier 会同时产生 100% burst 和自然 idle window，因此
单看平均 utilization 不能判断 worker 数是否合理。

## 9. 结论与限制

- HexAgenT 的 v0.5.15 Python planner、Rust router、global admission、snapshot、Mooncake
  P-D dispatch 和 DAG replay 已在真实 A100 上端到端跑通。
- ShareGPT 和 BFCL 的 P95 SLO ratio 优于 native baseline；Hotpot P95 近似持平略差，
  P99/max 更好。不能宣称三条 trace 的所有 tail 指标均胜出。
- 静态 worker registration 尚未自动携带 `hardware=A100` label。当前同构实验的 live
  snapshot/capacity 生效，但初始 roofline estimator 可能退回通用系数。异构实验前必须
  把 model/GPU/TP label 注入 router worker descriptor，并验证 estimator lookup。
- v0.5.15 仍不支持已 dispatch waiting request 的安全跨 worker live migration；安全的
  placement revision 仍限于 router global admission queue。
