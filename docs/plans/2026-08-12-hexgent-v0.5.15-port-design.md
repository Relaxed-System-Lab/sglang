# HexAgenT on SGLang v0.5.15: Port Design

## 1. Version and branch policy

HexAgenT remains available on two independent branches in the
`Relaxed-System-Lab/sglang` fork:

- `hexgent-v0.5.9-main`: preserved experiment-compatible implementation.
- `hexgent-v0.5.15`: implementation based on the upstream SGLang `v0.5.15`
  release tag (`f63458b5be`).

The v0.5.15 branch does not merge the old SGLang runtime wholesale.  Planner
semantics and HexAgenT interfaces are ported onto the v0.5.15 router, worker,
priority scheduling, retry, and disaggregation lifecycle.

## 2. Architecture retained by the port

The architecture remains split into three layers:

1. The Python planner owns workflow state, roofline latency estimation,
   projected-SLO-ratio ordering, prefill/decode placement, reservations, and
   optional local search.
2. The Rust PD router owns the global admission queue, event-driven planner
   refresh, current-plan publication, dispatch, fallback, bootstrap creation,
   worker mutation delivery, and completion events.
3. Python workers expose live snapshots and execute safe local priority
   updates.  Once prefill starts, the selected prefill/decode pair is immutable;
   the implementation does not attempt live KV migration.

Requests that have no HexAgenT decision must remain serviceable through the
native PD fallback.  Planner computation updates the current execution plan but
must not be a mandatory per-request blocking RPC.

## 3. v0.5.15 integration decisions

### 3.1 Native priority scheduling

SGLang v0.5.15 already propagates request priorities and supports priority-aware
queue ordering and preemption.  HexAgenT reuses these facilities instead of
maintaining a second local queue implementation.  HexAgenT-specific revision
checks remain necessary so stale planner actions cannot overwrite newer state.

### 3.2 Bootstrap and request lifecycle

The v0.5.15 Mooncake connection layer has stronger duplicate-room detection,
timeout cleanup, failure propagation, abort notification, and decode staging
state handling.  The router therefore creates the bootstrap assignment only at
actual dispatch.  Before dispatch, placement is a mutable router-owned plan;
after dispatch, only safe local priority changes are permitted.

### 3.3 Global cross-worker scheduling

v0.5.15 makes the implementation safer, but it does not provide transparent
live migration of a request and its partially produced KV cache.  Cross-worker
placement remains practical only while the request is in the router-owned
global admission queue.  A request already waiting at a worker can receive a
priority update, but changing its worker pair requires cancellation and a new
bootstrap and is not used by the production path.

### 3.4 Router adaptation

The v0.5.15 PD router uses prepared worker requests, policy registries, retry
configuration, circuit breaking, and typed outcomes.  HexAgenT is integrated as
an optional admission/placement controller around those facilities rather than
replacing them.  Native behavior remains the fallback and the non-HexAgenT
path.

## 4. Compatibility contract

The planner sidecar API remains compatible with the validated v0.5.9 branch:

- `GET /health`
- `POST /schedule_request` and `POST /plan`
- event-driven admission and revision publication endpoints
- `POST /event`

Workers retain these control interfaces:

- `GET /hexgent/pd_snapshot`
- `GET /hexgent/request_timing`
- `POST /hexgent/update_waiting_priority`
- `POST /hexgent/reassign_waiting`

`reassign_waiting` is restricted to states that have not started prefill and is
not treated as live migration.

## 5. Validation boundary

Local validation covers Python planner/worker tests, router argument tests,
formatting, and Rust static compilation where the host toolchain permits it.
The final acceptance test requires a Linux GPU Pod with Mooncake and the exact
v0.5.15 router extension rebuilt from this branch.
